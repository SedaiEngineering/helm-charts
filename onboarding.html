Kubernetes Cluster Integration

Smart Agent Installation Guide

Self-provisioning workflow, via Helm

This document provides step-by-step instructions for integrating Kubernetes with Sedai using our self-provisioning workflow. Instead of manually logging into the Sedai UI and following the standard integration process, deploy the Sedai Smart Agent directly into your Kubernetes cluster using an API key and our reusable Helm chart.

A custom job automatically creates the Kubernetes integration in Sedai and generates the necessary secret credentials within the cluster — faster onboarding, and a clean fit for Sedai as an add-on in your Infrastructure-as-Code templates.

Deployment Overview

This Helm chart deployment includes both the Smart Agent and the SmartAgentEnroll job.

Sedai Smart Agent

A deployment that runs within your Kubernetes cluster, enabling secure and continuous integration with the Sedai platform. It discovers cluster resources, synchronizes metrics, and executes optimization and discovery tasks received from Sedai using the appropriate RBAC permissions.

Sedai Pod Interceptor

A Kubernetes mutating admission webhook that runs inside your cluster. It applies Sedai's optimizations — CPU and memory, and optionally replica count and autoscaler bounds — at the moment Kubernetes admits an object, rather than by editing objects after the fact.

The key property: Sedai never writes optimized values into your Deployment manifests. Your Git repository stays the source of truth for everything you've written down — Sedai supplies only the values that couldn't be known when the manifest was authored.

Enabled by toggling sedaiPodInterceptor.enabled to true. Since the Pod Interceptor and its Postgres store are single-replica by design, they're also protected from Karpenter node-churn eviction — see Karpenter Disruption Protection in the FAQ.

Recommended

Sedai Smart Scheduler

Helps schedule and compact the cluster based on the resource requirements of your workloads and the configuration of your nodes / nodepools.

Enabled by toggling sedaiSmartScheduler.enabled and sedaiSmartScheduler.compactor.enabled to true.

Recommended

SmartAgentEnroll job

Automates onboarding and establishes the initial secure connection with the Sedai API Server:

  • Authenticates with the Sedai API Server using the provided API key.
  • Registers the Kubernetes cluster as an integration within Sedai.
  • Provisions Smart Agent–specific credentials, securely stored in a Kubernetes Secret.

The Smart Agent then consumes this secret for authenticated, continuous communication with Sedai.

  1. Authentication — establishes secure access to the Sedai API Server using the provided credentials.
  2. Integration registration — registers the Kubernetes cluster with Sedai, including cluster-specific details.
  3. Monitoring configuration — configures the monitoring provider within Sedai.
  4. Credential retrieval — securely retrieves integration-specific credentials from Sedai.
  5. Secret creation — creates a Kubernetes Secret containing the Smart Agent credentials and connection details.
  6. Smart Agent initialization — the agent starts only after successfully retrieving credentials.

Deployment Steps

Step 1

Generate a Sedai API key

The SmartAgentEnroll job authenticates with the Sedai API Server and automates onboarding. Generate an API key directly from the Sedai Dashboard, or ask our team to provide one — it can be reused across multiple cluster onboarding processes.

Login to the Sedai Dashboard → Settings → API Keys → Create New Key. Enter the key details and click Generate.

Step 2

Download the Helm chart

Pull the latest Helm chart from our repository (details below). Review values.yaml carefully and prepare your cluster-specific configuration before deploying.

Step 3

Create a custom-values file

Deploy this chart across all your Kubernetes clusters — use a cluster-specific values-override file for each. Below are examples for the major providers; see the FAQ for more.

In your override file, make sure to explicitly enable the Pod Interceptor (sedaiPodInterceptor.enabled: true) and the Smart Scheduler (sedaiSmartScheduler.enabled: true and sedaiSmartScheduler.compactor.enabled: true) — both are off by default, and we strongly recommend enabling them for every cluster (see Deployment Overview above for what each does). All four sample files below already turn them on.

Enable any listed integration by setting its enabled flag to true. Prometheus and VictoriaMetrics are mutually exclusive — pick one.

sedaiVictoriaMetrics:
  enabled: true
sedaiKSM:
  enabled: true
sedaiNodeExporter:
  enabled: true
sedaiBeyla:
  enabled: true
Recommended: VictoriaMetrics — lower memory footprint and better stability under load.
Note: sedaiPrometheus and sedaiVictoriaMetrics are for monitoring tools fully managed by Sedai. For your own self-hosted setup, use monitoringProvider instead — e.g. monitoringProvider.prometheus.

Step 4

Additional settings to avoid disruption

Before deploying, review these three settings and add whichever apply to your environment — each addresses an issue that otherwise only shows up after the cluster is already onboarded.

DNS resolution — clusterDomain

If a cluster's kubelet/CoreDNS domain configuration is non-standard, the Smart Agent can fail to reach the Pod Interceptor with a Name does not resolve error. Set this up front if you know your cluster is affected (see FAQ #14 for the full symptom):

clusterDomain: "cluster.local"

Deploying via ArgoCD — ignoreDifferences

If you're deploying via ArgoCD, you must include ignoreDifferences in your Application manifest — without it, dynamically generated secrets and mutated webhook configuration created at runtime will cause sync loops. This is not optional; see FAQ #13 for the complete ignoreDifferences block to copy into your Application manifest.

Karpenter clusters — disruptionProtection

If your cluster runs Karpenter, its node consolidation/expiration can evict the Smart Agent, Pod Interceptor (+ its DB), Smart Scheduler, or compactor as it churns nodes — which shows up as their health flapping. This is on by default, but confirm it's set for each component you've enabled (see FAQ #15 for what it does):

workload:
  smartAgent:
    disruptionProtection: true

sedaiPodInterceptor:
  disruptionProtection: true

sedaiSmartScheduler:
  disruptionProtection: true
  compactor:
    disruptionProtection: true

Step 5

Deploy Sedai Smart Agent

Deploy the chart to your cluster, overriding cluster-specific details with your values-override file.

cd sedai-smart-agent
helm upgrade --install sedai-smart-agent -n sedai-smart-agent \
  --create-namespace -f values.yaml -f values-override-clustername.yaml .

FAQ

01

Do I need to create a custom values.yaml file?

Yes. You can reuse the same Helm chart and API key to onboard multiple Kubernetes clusters to Sedai. For easier management, create a custom values.yaml file per cluster — this simplifies upgrades, supports GitOps-based management, and keeps cluster-specific configuration organized.

02

Providing the Sedai API key via Kubernetes Secret

Instead of specifying the API key directly in values.yaml, provide it securely via a Kubernetes Secret. Create the Secret using your preferred method and reference its name and key:

sedaiIntegrationSettings:
  sedaiApiTokenSecret: ""     # Name of the Kubernetes Secret that stores the token
  sedaiApiTokenSecretKey: ""  # Key within the Secret that stores the token

03

What endpoints need to be whitelisted?

The Smart Agent initiates all outbound connections — to the Sedai API endpoint over HTTPS/WebSocket (port 443), and telemetry to Sedai's centralized platform. Whitelist for outbound access on port 443:

  • tenant.sedai.app — Sedai API and WebSocket communication (or your BYOC endpoint, air-gapped environments)
  • gw.sedai.cloud — Smart Agent telemetry logs

04

How do I disable telemetry log streaming to gw.sedai.cloud?

By default the Smart Agent streams telemetry logs there. If egress is restricted, or you'd rather view logs in-console for debugging:

enableAgentDebugLogs:
  enabled: true

05

Image pull secret

Pulling from a private registry (e.g. Sedai's ACR)? Configure a pull secret:

imagePullSecret:
  enabled: true
  secretName: ""

Requires a Kubernetes secret in the Smart Agent's namespace containing .dockerconfigjson. For Sedai's ACR:

kubectl create secret docker-registry sedai-acr-secret \
  --docker-server=sedai.azurecr.io \
  --docker-username=<ACR_USERNAME> \
  --docker-password='<ACR_PASSWORD>' \
  -n sedai-smart-agent

06

Can I deploy with ReadOnly permissions for a POC?

Yes. By default a cluster onboards in Data Pilot Mode — collecting data without making changes. To enforce read-only mode at the cluster level:

sedaiIntegrationSettings:
  rbacReadOnly: true

07

Can I add multiple monitoring providers for a cluster?

Yes — configure multiple monitoring providers for a single cluster integration. See the monitoringProvider section of values.yaml for the supported list. Provider missing? Reach out — we're continuously adding more.

08

Can I delete the Sedai integration automatically on decommission?

Yes, via a post-delete hook job:

sedaiIntegrationSettings:
  enableDeRegisterJob: true

Uninstalling the Helm chart will then automatically delete the corresponding Sedai integration.

09

Google Cloud Monitoring with a Service Account key

Requires a GCP Service Account with Monitoring Viewer and Compute Viewer roles. Two ways to supply the key:

  • Add the JSON directly to monitoringProvider.serviceAccountKeyJson — not recommended for production.
  • Create a Kubernetes Secret and reference it via monitoringProvider.gcpSecret / gcpServiceAccountKeySecretKey — recommended.
monitoringProvider:
  gcpMonitoring:
    enabled: true
    projectID:
    serviceAccountKeyJson:
    gcpSecret:
    gcpServiceAccountKeySecretKey:

10

How do I keep my Smart Agent version up to date?

helm repo update
helm pull sedai/sedai-smart-agent --untar

Downloads the latest chart — updated images, chart enhancements and bug fixes, configuration improvements. Review release notes / values.yaml for new options before upgrading.

11

What is Sedai Managed Victoria Metrics?

A lightweight, preconfigured Victoria Metrics setup bundled with the chart, for clusters without an existing monitoring provider or unable to grant external access. Minimal scrape configuration, 3-hour default retention. Optionally pair with Kube State Metrics + Node Exporter, Grafana Beyla (eBPF network observability), or Grafana Alloy (unified alternative to both). Sedai doesn't modify these open-source components — only their configuration, for efficiency and compatibility.

12

How do I delete the Sedai Kubernetes integration?

From the Sedai Administration UI directly — or automatically, if sedaiIntegrationSettings.enableDeRegisterJob: true and you uninstall the chart. Deleting an integration permanently removes all collected data; re-adding the same cluster later starts as a new integration with no history retained.

13

Can I deploy via ArgoCD?

Yes — via ArgoCD or any GitOps provider.

Critical: include ignoreDifferences in your Application manifest. Without it, dynamically generated secrets and mutated webhook configuration created at runtime will cause sync loops.
apiVersion: argoproj.io/v1alpha1
kind: Application
metadata:
  name: sedai-smart-agent
  namespace: argocd
spec:
  project: sedai-integration   # Update your Project Name here
  source:
    repoURL: https://sedaiengineering.github.io/helm-charts
    chart: sedai-smart-agent
    targetRevision: 2.0.8   # Update Latest Helm Chart Version here
    helm:
      values: |
        sedaiVictoriaMetrics:
          enabled: true
        sedaiKSM:
          enabled: true
        sedaiNodeExporter:
          enabled: true
        sedaiBeyla:
          enabled: true
        sedaiPodInterceptor:
          enabled: true
        sedaiSmartScheduler:
          enabled: true
          compactor:
            enabled: true
        sedaiIntegrationSettings:
          nickName: "your-k8s-cluster-nickname"
          clusterName: "your-k8s-cluster"
          clusterProvider: "AWS"
          sedaiBaseUrl: "https://tenant.sedai.app"
          sedaiApiTokenSecret: ""
          sedaiApiTokenSecretKey: ""

  destination:
    server: https://kubernetes.default.svc
    namespace: sedai-smart-agent

  syncPolicy:
    automated:
      prune: true
      selfHeal: true
    syncOptions:
      - CreateNamespace=true

  ignoreDifferences:
    - group: ""
      kind: Secret
      name: sedai-kube-spec-controller-db
      namespace: sedai-smart-agent
      jsonPointers:
        - /data/password
    - group: ""
      kind: Secret
      name: sedai-kube-spec-controller-tls
      namespace: sedai-smart-agent
      jsonPointers:
        - /data/ca.crt
        - /data/tls.crt
        - /data/tls.key
    - group: admissionregistration.k8s.io
      kind: MutatingWebhookConfiguration
      name: sedai-kube-spec-controller-mutation-webhook-sedai-smart-agent
      jqPathExpressions:
        - '.webhooks[].clientConfig.caBundle'

14

My cluster's DNS resolution is misconfigured — the Pod Interceptor can't reach its Service

The Smart Agent reaches the Pod Interceptor over the short-form Service DNS name (<svc>.<namespace>.svc), relying on the pod's search-domain expansion to append the cluster's real domain (normally cluster.local). This works on virtually all clusters. If a cluster's kubelet/CoreDNS domain configuration has drifted apart and that expansion is failing — symptom: a Java/JVM Name does not resolve error on a *.svc address that otherwise resolves fine with the full FQDN appended — set clusterDomain to force fully-qualified Service DNS names instead:

clusterDomain: "cluster.local"   # -> sedai-kube-spec-controller-svc.<namespace>.svc.cluster.local

Leave empty (the default) unless you're hitting that specific symptom.

15

Karpenter Disruption Protection

If your cluster runs Karpenter, its node consolidation/expiration can evict any pod as it churns nodes — for the Smart Agent, the Pod Interceptor (+ its DB), the Smart Scheduler, and the compactor, that shows up as their health flapping. This is separate from the sedaiKarpenter.enabled toggle (which opts the cluster in to Sedai deploying and managing Karpenter itself) — disruption protection applies whenever Karpenter is managing your nodes, whether or not Sedai deployed it.

Each of those four components has its own disruptionProtection value (default true) that adds the karpenter.sh/do-not-disrupt: "true" annotation to the pod, so Karpenter skips proactively consolidating any node hosting it:

workload:
  smartAgent:
    disruptionProtection: true

sedaiPodInterceptor:
  disruptionProtection: true

sedaiSmartScheduler:
  disruptionProtection: true
  compactor:
    disruptionProtection: true

Set any of these to false to let Karpenter churn that component's nodes freely.
